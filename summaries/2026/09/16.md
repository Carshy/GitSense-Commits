### Patterns and Recurring Elements:

1.  **Schema Definition with Drizzle ORM:** The project heavily utilizes Drizzle ORM for schema definition in PostgreSQL, importing various column types (`uuid`, `varchar`, `integer`, `boolean`, `pgEnum`, `timestamp`) and schema features (`index`, `uniqueIndex`, `check`).
2.  **Data Integrity through `check` and `uniqueIndex` Constraints:** A consistent pattern is observed where `check` constraints are added post-initial schema creation to enforce business rules (e.g., non-negative quantities/amounts, specific relationships). `uniqueIndex` with `where` clauses is used to enforce uniqueness under certain conditions (e.g., active cart per user).
3.  **Modular Schema Organization with Relations:** Schemas are broken down into logical files (e.g., `product-variants.schema.ts`, `inventory.schema.ts`, `carts.schema.ts`). Corresponding `*-relations.ts` files (e.g., `catalog-relations.ts`, `cart-relations.ts`, `checkout-relations.ts`, `order-relations.ts`, `payment-relations.ts`) are created to centralize and define the relationships between these entities using Drizzle's `relations` API.
4.  **Centralized Schema Export:** The `index.ts` file in the `db/schema` directory serves as a single point of aggregation, importing and re-exporting all individual schema and relation files. This file is updated progressively as new database modules are developed.
5.  **Standard Timestamps and UUIDs:** Almost all tables consistently include `id` as a `uuid().defaultRandom().primaryKey()`, along with `createdAt` and `updatedAt` fields using `timestamp().defaultNow().notNull()`, indicating a standard approach for primary keys and auditing timestamps.
6.  **Domain-Driven Design (DDD) in Payment Module:** The payments module demonstrates a clear DDD structure:
    *   **Domain Enums:** Dedicated files for defining enums (`payment-status.ts`, `payment-attempt-status.ts`, `payment-provider.ts`, `payment-method.ts`) to represent core concepts.
    *   **Domain Value Objects:** The `money.ts` file provides an immutable `Money` value object, encapsulating financial logic and ensuring data consistency.
    *   **Domain Repositories:** Interfaces (`payment-repository.ts`, `payment-attempt-repository.ts`) define the contract for data access, abstracting away implementation details.
    *   **Infrastructure Implementations:** `drizzle-payment-repository.ts` and `drizzle-payment-attempt-repository.ts` provide the concrete Drizzle ORM implementations for these domain repository interfaces.
    *   **External Provider Interfaces:** `payment-provider.ts` defines the contract for integrating with external payment service providers.
7.  **Progressive Type Refinement:** Within the payment module, an evolution is seen from generic string types (e.g., for provider names) to more specific, enum-backed types (`PaymentProviderType`, `PaymentMethod`), improving type safety and code readability over time.
