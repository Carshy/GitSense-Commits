### Patterns and Recurring Elements:

*   **Drizzle ORM Usage:** All schema definitions consistently use `drizzle-orm/pg-core` for PostgreSQL table creation, indicating a strong adherence to a Drizzle-based ORM strategy.
*   **UUID Primary Keys:** `uuid("id").defaultRandom().primaryKey()` is the standard pattern for primary keys across all tables, ensuring unique, database-generated IDs.
*   **Timestamping:** `createdAt` and `updatedAt` fields with `defaultNow().notNull()` are ubiquitous for tracking record creation and modification times, along with `deletedAt` for soft deletes in some tables.
*   **Enum-Driven Statuses:** Extensive use of `pgEnum` for defining and enforcing valid states for various entities (e.g., product variant concentration/status, cart status, checkout status, order status/payment/fulfillment, payment provider/method/status, payment attempt status, webhook status). This promotes data consistency and type safety.
*   **Declarative Constraints:** Complex data validation rules are enforced using Drizzle's `check` function with `sql` expressions (e.g., ensuring positive quantities/amounts, non-negative totals, non-zero changes, and logical conditions like "exactly one owner").
*   **Indexing Strategy:** `index` is widely used on foreign keys and frequently searched columns to optimize query performance. `uniqueIndex` is applied where data uniqueness is critical (e.g., SKU, order numbers, active carts per user/guest, single address per checkout).
*   **Separation of Concerns for Relations:** Dedicated `*-relations.ts` files are created for each major domain (catalog, cart, checkout, order, payment) to define `drizzle-orm` relations, promoting modularity and readability.
*   **Central Schema Export:** The `src/db/schema/index.ts` file serves as a barrel file, consolidating exports of all schema and relation definitions. This file is consistently updated as new schema components are added, simplifying imports elsewhere in the application.
*   **Domain-Driven Design in Payments Module:** The payments module demonstrates a clear separation between domain interfaces (`payment-status.ts`, `payment-attempt-status.ts`, `payment-repository.ts`, `payment-attempt-repository.ts`) and infrastructure provider interfaces (`payment-provider.ts`), indicating an architectural pattern aimed at maintainability and testability.
